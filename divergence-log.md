# Parity divergence log

> **Closed — historical record.** The Angular target has been retired and the suite now runs against the Nuxt app
> alone, so no new divergences are recorded here. The entries below are kept because they carry the *reasons* the
> rewrite behaves as it does; several assertions in the suite still have the shape they do because of them.

Every intended difference between the Angular app and the Nuxt rewrite was recorded here — so a difference surfaced
during the cutover soak was recognised as **intended**, never mistaken for a regression, and a parity assertion was
never silently loosened.

The suite was authored against the Angular app and asserts user-visible outcomes only, so the identical journeys ran
against the rewrite. Two kinds of divergence exist:

1. **Assertion-affecting** — the intended difference forced a parity assertion to accept both behaviours (or made a
   check Nuxt-only). Table in §1.
2. **Behavioural, assertion-neutral** — the apps differ, but the user-visible outcome the journeys assert is the same.
   Listed in §2 so operators watching the cutover know these are by design.

## 2. Behavioural differences (parity assertions unaffected)

Intended by the rewrite's design decisions. The journeys still pass against both targets because the **user-visible outcome they
assert is identical** — only the mechanism differs, so these are logged for cutover awareness.

| Area                        | Angular (legacy)                                                                                   | Nuxt rewrite                                                                                                                        | Reason                                                                                                                                                 |
|-----------------------------|----------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Network topology / auth** | Browser calls Spring directly; OIDC tokens live in the browser; Spring needs a browser CORS origin | Browser only ever talks to the Nuxt origin (BFF); tokens held server-side in two sealed cookies; Spring is private, no browser CORS | The BFF. Invisible to the journeys (same sign-in outcome) but it changes the deploy topology (runbook §0)                                              |
| **Session lifetime**        | Deferred to the IdP token lifetime                                                                 | Server-side two-tier lifetime: absolute cap (`session.maxAge`, 8 h) + sliding idle-timeout (`session.idleMaxAge`, 30 min)           | A user idle > 30 min is re-authenticated.   Won't surface in a journey (they don't idle), but operators will see idle logouts by design                |
| **Backend API version**     | `/api/v1`                                                                                          | `/api/v2` for all domain work (v1 only for the current-user/auth endpoint)                                                          | v2 is tenant-first (paging/sort/ETag differ internally); the user-visible data is the same. v1 stays alive under its sunset policy during the dual-run |
| **UI toolkit**              | Angular + PrimeNG                                                                                  | Vue 3 / Nuxt 4 SSR + Ant Design Vue                                                                                                 | The rewrite's stack.         Markup and CSS classes differ entirely — which is exactly why the parity suite selects by role/text, never CSS            |
| **Correlation id**          | none                                                                                               | Every proxied response carries `X-Correlation-Id`; the same id reaches Spring's audit trail                                         | Additive, response-header only; no journey asserts it                                                                                                  |
| **Responsive / theming**    | Desktop-oriented; single theme                                                                     | Mobile-first down to a 320 px floor; SYSTEM/LIGHT/DARK with AA contrast in both modes                                               | The parity suite runs at the desktop viewport, so it neither exercises nor contradicts this                                                            |

## How to add an entry

When authoring or updating a journey, if the two targets differ:

- **Changes a user-visible outcome the suite asserts** → add a row to §1 and make the assertion accept the intended
  behaviour explicitly (prefer the rewrite's behaviour, keep the legacy path as a labelled fallback). Never loosen an
  assertion to "pass on both" without recording why.
- **Same outcome, different mechanism** → add a row to §2.

The full suite green against both targets, with every diff accounted for here, was the objective cutover gate (runbook
§1). With Angular retired, `pnpm test:nuxt` green is the standing gate.
